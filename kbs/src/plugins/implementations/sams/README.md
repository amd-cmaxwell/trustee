# Signing, Authorization, & Measurement Service (SAMS)

Background
---
Provides CVM-Launch-Measurement-as-a-Service functionalities.

Why?
---
1. Offers verifiers AS STRONG a guarantee that an attester launched with a specific configuration as does verifying the launch measurement in an attestation report against a list of reference values.
2. Makes Attestation Reports generated by Pre-Verified CVMs reflect an endorsement from Trustee
3. Facilitates the transition from storing and comparing opaque pre-computed launch measurements in RVPS to storing and comparing modular values for specific launch parameters

API
---

> For full request/response schemas see [Demystifying the Measurement Endpoints](demystifying-the-measurement-endpoints.md).
> For the dynamic auth key design rationale see [Addendum on Dynamic Auth Keys](addendum-on-dynamic-auth-keys.md).

### POST /measurement/\<tee\>/
#### Requires Admin?
- No
#### Request Params:
- A JSON Object containing:
1. All params required to create a Launch Measurement (e.g. vcpus, vcpu_type, vmm_type, guest_features, append)
2. Precomputed hashes of the Kernel, Initrd, & OVMF (e.g. kernel_hash_str, initrd_hash_str, ovmf_hash_str)
3. [Optional] IDBlock Metadata: FAMILY_ID & IMAGE_ID

#### Response (progressive):
- **Launch params only:** `{"measurement": "<launch measurement>"}`
- **Launch params + IDBlock Metadata:** adds `"id-block"` (base64-encoded IDBlock containing the measurement, FAMILY_ID, IMAGE_ID, and GUEST_SVN set to the current MAGS from RVPS)

---

### POST /measurement/\<tee\>/auth
#### Requires Admin?
- No
#### Headers:
- `Authorization: Bearer <JWT containing "guest-owner-cert": "<mTLS Certificate>">`  _(optional)_
#### Request Params:
- Same as `POST /measurement/<tee>/`, but IDBlock Metadata (FAMILY_ID & IMAGE_ID) is **required**
#### Response (progressive):
- **Launch params + IDBlock Metadata + SAMS policy approval:**
  - `"measurement"`, `"id-block"` (as above)
  - `"id-auth"` (base64-encoded IdAuth with SAMS-only signing: AuthKey fields zeroed)
  - `"id-key"` (SAMS Public Key)
- **All of the above + registered guest-owner mTLS cert in Bearer Token:**
  - `"id-auth"` includes guest-owner signing (IdKeySig, AuthKeyAlgo, AuthKeyDigest populated)
  - `"author-key"` (Guest Owner Public Key)
#### Error Codes:
- `400` — missing required launch params or IDBlock metadata
- `401` — malformed/expired Bearer Token, invalid cert, or unknown guest-owner
- `403` — SAMS policy rejects launch params, IDBlock metadata, and/or mTLS cert

### POST /guest-owner
#### Requires Admin?
- No (mTLS-authenticated)
#### Prerequisites:
- Connection must use mTLS. Both the guest owner and SAMS must have leaf certificates issued by a mutually trusted TLS Certificate Authority.
#### Request Params:
```json
{
    "pubkey": "<Guest Owner Signing Public Key>",
    "privkey": "<Guest Owner Signing Private Key>"
}
```
#### Behavior:
- Stores the guest owner's mTLS leaf cert in RVPS (keyed by `hash(<pubkey>)`)
- Stores the guest owner's signing keypair in KBS (keyed by `hash(<leaf-cert>)`)
#### Expected usage:
```shell
curl \
    --cert guest-owner-mTLS-leaf-cert-chain.crt \
    --key guest-owner-mTLS-leaf-cert-private-key.key \
    --cacert ca.crt \
    -X POST http://$kbs_host:$kbs_api_port/kbs/v0/sams/guest-owner \
    -d '{"pubkey": "...", "privkey": "..."}'
```

> See [Addendum on Dynamic Auth Keys](addendum-on-dynamic-auth-keys.md) for the full design rationale.

---

### DELETE /guest-owner
#### Requires Admin?
- No (mTLS-authenticated)
#### Prerequisites:
- Connection must use mTLS (same CA requirements as registration).
#### Behavior:
Upon completion of the mTLS handshake:
1. Hash the guest owner's leaf cert
2. Retrieve the guest owner's signing keypair from KBS using that hash
3. Hash the signing pubkey
4. Remove the guest owner's leaf cert from RVPS (keyed by pubkey hash)
5. Remove the guest owner's signing keypair from KBS (keyed by leaf cert hash)
#### Expected usage:
```shell
curl \
    --cert guest-owner-mTLS-leaf-cert-chain.crt \
    --key guest-owner-mTLS-leaf-cert-private-key.key \
    --cacert ca.crt \
    -X DELETE http://$kbs_host:$kbs_api_port/kbs/v0/sams/guest-owner
```

enables pre-verification via SAMS. Kubernetes forwards the request to the Kata Runtime.

##### 2. ID Block Generation via SAMS

When `requirePreVerification` is true, Kata Runtime requests an ID Block from
the SAMS plugin. SAMS optionally pre-verifies each launch parameter against RVPS
reference values before computing the expected launch measurement and signing the
ID Block. SAMS retrieves the current Minimum Acceptable Guest SVN (MAGS) from
RVPS and embeds it in the ID Block as the GUEST_SVN, versioning the block so
that stale ID Blocks can be rejected during attestation.

If `requirePreVerification` is not true, the current (non-SAMS) flow is used and
the CVM is launched without an ID Block.

When the request targets the `/auth` endpoint and includes a Bearer Token with a
registered guest owner's mTLS certificate, SAMS also signs the IDKey with the
guest owner's private key (stored in KBS), producing a full IdAuth with non-zero
AuthKey fields. See [Addendum on Dynamic Auth Keys](addendum-on-dynamic-auth-keys.md)
for the full design rationale.

```mermaid
sequenceDiagram

    participant api as Trustee API
    participant sams as SAMS Plugin
    participant policy_engine as Policy Engine<br>(Regorus)
    participant rvps as RVPS
    participant kbs as KBS

        note left of kata_runtime: Fallback: launch CVM<br>without ID Block<br>(current flow)
    else requirePreVerification is true
        kata_runtime ->> api: POST /measurement/snp<br>or POST /measurement/snp/auth
        api ->> sams: Forward request

        note over kata_runtime, sams: LaunchParams = {vcpus, ovmf_hash,<br>kernel_hash, initrd_hash, ...}
        note over kata_runtime, sams: ID Block Metadata = {family_id,<br>image_id, guest_policy}

        opt Guest-owner cert in Bearer Token
            sams ->> kbs: Retrieve guest-owner signing keypair<br>(keyed by hash of mTLS cert)
            break Cert unknown to KBS
                sams -->> kata_runtime: 401 - Unauthorized
            end
            kbs -->> sams: Guest-owner keypair
        end

        opt Pre-Verification against RVPS
            sams ->> policy_engine: Register query_reference_value extension
            sams ->> policy_engine: Evaluate Launch policy
            note over sams, policy_engine: input = LaunchParams<br>(+ mTLS cert if present)<br>rules = [data.policy.authorized,<br>data.policy.extensions]
            note over policy_engine: Policy can also assert on<br>mTLS cert fields<br>(Subject, Extensions, etc.)
            policy_engine ->> rvps: Query reference values (per rule)
            rvps -->> policy_engine: Reference values
            policy_engine ->> policy_engine: Compare launch params against values
            policy_engine -->> sams: Pre-Validation Result
            break Launch Params Rejected
                sams -->> kata_runtime: Error: Pre-verification failed
                note over sams: ID Block not issued
            end
        end

        critical Version the IDBlock
            sams ->> rvps: Get Minimum Accepted <br>Guest SVN (MAGS)
            rvps -->> sams: MAGS Value
        end
        note over sams: From LaunchParams,<br> IDBlock Meta,<br> & MAGS Value
        sams ->> sams: Calculate Launch Measurement<br>(sev-snp-measure / create_id_block)
        sams ->> sams: Sign IDBlock with SAMS PrivKey

        alt /measurement/snp (unauthenticated)
            sams -->> kata_runtime: ID Block response
            note over sams, kata_runtime: Response contains:<br>- measurement<br>- id-block (if IDBlock metadata provided)
        else /measurement/snp/auth (no guest-owner cert)
            sams ->> sams: Create IdAuth (SAMS-only signing,<br>AuthKey fields zeroed)
            sams -->> kata_runtime: ID Block + IdAuth response
            note over sams, kata_runtime: Response contains:<br>- measurement, id-block<br>- id-auth (SAMS-only)<br>- id-key (SAMS PubKey)
        else /measurement/snp/auth (with guest-owner cert)
            sams ->> sams: Sign IDKey with guest-owner PrivKey
            sams ->> sams: Create IdAuth (full signing)
            sams -->> kata_runtime: ID Block + IdAuth response
            note over sams, kata_runtime: Response contains:<br>- measurement, id-block<br>- id-auth (full: IDBlockSig + IdKeySig)<br>- id-key (SAMS PubKey)<br>- author-key (Guest Owner PubKey)
        end
    end
```

##### 3. CVM Launch & Firmware Verification

Kata Runtime passes the SAMS-provided id-block and id-auth directly to the
hypervisor. When SAMS handled guest-owner authentication (via the `/auth`
endpoint), the id-auth already contains the full IdAuth with AuthKey signing
performed inside SAMS using the guest owner's private key stored in KBS.
SNP firmware verifies the signatures and compares the actual launch measurement
against the expected value in the ID Block.

```mermaid
sequenceDiagram
    participant fw as SNP Firmware
    participant hv as Hypervisor (QEMU)
    participant kata_runtime as Kata Runtime<br>(on Untrusted Host)

    kata_runtime ->> kata_runtime: Encode hypervisor params<br>from SAMS response
    note over kata_runtime: id-block = SAMS-provided id-block<br>id-auth = SAMS-provided id-auth<br>(AuthKey signing done by SAMS)
    note over kata_runtime: author-key-enabled =<br>1 if SAMS response contained "author-key",<br>0 otherwise

    kata_runtime ->> hv: Launch CVM with ID Block
    note over kata_runtime, hv: -object sev-snp-guest,<br>id-block=...,<br>author-key-enabled=0|1,<br>id-auth=...,<br>...
    hv ->> fw: SNP_LAUNCH

    critical SNP_LAUNCH_FINISH
        fw ->> fw: Verify signature fields
        fw ->> fw: Calculate actual launch measurement
        fw ->> fw: Compare actual vs expected measurement

        alt Verification succeeds
            fw ->> hv: ALLOW CVM creation (with guest context)
            note over fw, hv: CVM boots with guest context containing<br> ID Block,<br> ID Auth,<br>& Host Data <br> + With InitData file mounted RO
            hv -->> kata_runtime: CVM booted
        else Verification fails
            break AuthKeyDigest mismatch
                fw ->> hv: Abort CVM boot
            end
            break IDKeyDigest mismatch
                fw ->> hv: Abort CVM boot
            end
            break Measurement mismatch
                fw ->> hv: Abort CVM boot
            end
            note over fw, hv: CVM FAILS TO START
        end
    end
```

##### 4. RCAR Handshake & Attestation Report

Once the CVM is running, the Confidential Data Hub (CDH) needs secrets (e.g. image
decryption keys) from the KBS. It performs the RCAR handshake in three steps: first,
it authenticates via `POST /kbs/v0/auth` and receives a session cookie and challenge
nonce. Next, it requests an attestation report from SNP firmware, binding the nonce
and TEE public key into REPORT_DATA. The resulting report also carries the HOST_DATA
set at launch, along with the IDBlock and IDAuth fields. Finally, CDH submits the
report to `POST /kbs/v0/attest` with the tee-evidence (the attestation report),
runtime-data (the nonce and TEE public key whose hash must match REPORT_DATA),
and optionally init-data.

```mermaid
sequenceDiagram
    participant fw as SNP Firmware
    participant cdh as Confidential Data Hub<br>(in CVM)
    participant api as Trustee API
    participant trustee_as as Attestation Service

    note over cdh: Needs image decryption key<br>from KBS, but must attest first

    critical RCAR Handshake
        cdh ->> api: POST /kbs/v0/auth
        note over cdh, api: body: {version, tee, extra-params}
        api -->> trustee_as: Forward auth request
        trustee_as -->> cdh: Session Cookie +<br>Challenge (nonce + optional extra params)

        cdh ->> fw: Request Attestation Report
        note over cdh, fw: REPORT_DATA <br>= hash(nonce + TEE PubKey)
        fw -->> cdh: Attestation Report
        note over fw, cdh: Report contains:<br><br>- REPORT_DATA = <br>(hash of nonce & TEE PubKey hash)<br><br>- HOST_DATA =<br>(hash of initData)<br><br>- IDBlock & IDAuth fields

        cdh ->> api: POST /kbs/v0/attest
        api -->> trustee_as: Forward attestation request
        note over cdh, api: Header: Cookie kbs-session-id=...<br>Body: {tee-evidence, runtime-data,<br>init-data (optional)}
        note over cdh, api: runtime-data (REQUIRED):<br>RCAR nonce + TEE PubKey<br>(Hash MUST match REPORT_DATA)
        note over cdh, api: tee-evidence (REQUIRED):<br>Attestation Report <br>as primary_evidence
        note over cdh, api: init-data (OPTIONAL):<br> Trustee Config files
    end
```

##### 5. Attestation Verification & Policy Evaluation

The SNP Verifier validates the attestation report in three stages: first, it verifies the
AMD certificate chain (hardware endorsement); second, it checks that the hashes of the
provided initdata and runtimedata match the HOST_DATA and REPORT_DATA fields in the report.
The verified claims are then evaluated by the Policy Engine against the EAR appraisal policy.
Policy provisions can query RVPS for reference values, verify the reported GUEST_SVN against
the Minimum Acceptable Guest SVN (MAGS) from RVPS, and verify the Trustee endorsement by
comparing the IDKeyDigest against acceptable SAMS public key hashes from RVPS. When a
guest owner registered their signing keypair via SAMS, verifier policies can also look up
the guest owner's mTLS leaf cert from RVPS using the AuthKeyDigest as the retrieval key,
and make assertions about the certificate's Subject and Extensions fields. Any mismatch
adjusts the trust claims at a severity determined by the Verifier Policy Owner. The final
result is an EAR token encoding the TEE's trustworthiness vector.

```mermaid
sequenceDiagram
    participant cdh as Confidential Data Hub<br>(in CVM)
    participant snp_verifier as SNP Verifier
    participant policy_engine as Policy Engine<br>(Regorus)
    participant rvps as RVPS

    critical Verify hardware endorsements
        snp_verifier ->> snp_verifier: Verify AMD certificate chain
        break Signature mismatch
            note over snp_verifier: Report not trusted<br>by HW manufacturer
        end
    end

    critical Verify user-defined report fields
        snp_verifier ->> snp_verifier: Hash provided initdata & runtimedata
        snp_verifier ->> snp_verifier: Compare against HOST_DATA<br>& REPORT_DATA in report
        break initdata hash mismatch
            note over snp_verifier: CVM may be in a<br>non-compliant state
        end
        break runtimedata hash mismatch
            alt Nonce mismatch
                note over snp_verifier: Potential replay attack
            else TEE PubKey mismatch
                note over snp_verifier: Potential MITM attack
            end
        end
    end

    critical Evaluate appraisal policy
        snp_verifier ->> policy_engine: Register query_reference_value extension
        snp_verifier ->> policy_engine: Evaluate EAR policy for TEE class
        note over snp_verifier, policy_engine: input = claims from report,<br>initdata, & runtimedata<br>rules = [data.policy.trust_claims,<br>data.policy.extensions]

        loop For each policy provision
            opt Provision queries reference values
                policy_engine ->> rvps: Retrieve reference values
                rvps -->> policy_engine: Reference values
                policy_engine ->> policy_engine: Compare claims against values
            end
        end

        opt Verify Guest SVN
            policy_engine ->> rvps: Retrieve Minimum Acceptable Guest SVN (MAGS)
            rvps -->> policy_engine: MAGS Value
            policy_engine ->> policy_engine: Compare Reported Guest SVN<br> against MAGS Value
            break Reported Guest SVN non-compliant
                policy_engine ->> policy_engine: Adjust trust claims
                note over policy_engine: Severity determined by<br>Verifier Policy Owner
            end
        end

        opt Verify Trustee endorsement (IDKeyDigest)
            policy_engine ->> rvps: Retrieve acceptable<br>SAMS public key hashes (SHA-384)
            rvps -->> policy_engine: Acceptable public key hashes
            policy_engine ->> policy_engine: Compare IDKeyDigest<br>against acceptable hashes
            break No IDKeyDigest match
                policy_engine ->> policy_engine: Adjust trust claims
                note over policy_engine: Severity determined by<br>Verifier Policy Owner
            end
        end

        opt Verify Guest Owner identity (AuthKeyDigest)
            policy_engine ->> rvps: Retrieve guest-owner mTLS leaf cert<br>(keyed by AuthKeyDigest)
            rvps -->> policy_engine: Guest-owner mTLS certificate
            policy_engine ->> policy_engine: Assert against cert fields<br>(Subject, Extensions, etc.)
            break Guest-owner cert assertion fails
                policy_engine ->> policy_engine: Adjust trust claims
                note over policy_engine: Severity determined by<br>Verifier Policy Owner
            end
        end

        policy_engine -->> snp_verifier: Trust claims (map of i8 integers)
        snp_verifier ->> snp_verifier: Convert to AR4SI Trustworthiness Vector
    end

    critical Issue EAR Token
        snp_verifier ->> snp_verifier: Create JWT bound to HTTP session
        note over snp_verifier: Contains: trustworthiness vector,<br>expiration (default TTL: 5 min)
        snp_verifier -->> cdh: EAR Token (RCAR handshake complete)
    end
```

##### 6. Secret Release & Pod Launch

The CDH presents the EAR token to request resources from the KBS. The KBS evaluates
the token against its resource policy; if allowed, the secret is released (optionally
encrypted with the TEE's public key). The CDH decrypts image layers and the pod launches.

```mermaid
sequenceDiagram
    participant k8s as Kubernetes<br>(on Untrusted Host)
    participant kata_runtime as Kata Runtime<br>(on Untrusted Host)
    participant kata_agent as Kata Agent<br>(in CVM)
    participant cdh as Confidential Data Hub<br>(in CVM)
    participant image_repo as Container Image Repository
    participant api as Trustee API
    participant kbs as KBS
    participant policy_engine as Policy Engine<br>(Regorus)
    participant kbs_resource as KBS Resource Plugin

    k8s ->> kata_runtime: Launch Pod <br>from encrypted image
    kata_runtime ->> kata_agent: Forward Request
    kata_agent ->> cdh: Pull encrypted image

    loop For each image layer
        cdh ->> image_repo: Fetch compressed image layer
        image_repo -->> cdh: Image Layer
        cdh -->> cdh: Extract Image Layer

        opt Layer is encrypted
            cdh ->> cdh: Extract decryption key URI from annotations

            cdh ->> api: GET /resource/v0/repo/type/tag (+ EAR Token)
            api -->> kbs: Forward request

            critical Evaluate KBS Resource Policy
                kbs ->> kbs: Parse URL path and query params
                kbs ->> policy_engine: Evaluate policy
                note over kbs, policy_engine: data = {plugin, resource-path, query}<br>input = claims from EAR Token<br>rule = data.policy.allow

                alt Policy denies access
                    policy_engine -->> kbs: ACCESS DENIED
                    break when access denied
                    note over kbs,cdh: Pod not started,<br> CVM SHUTDOWN
                    end
                else Policy allows access
                    policy_engine -->> kbs: Allow
                    kbs ->> kbs_resource: Retrieve resource
                    kbs_resource -->> kbs: Resource payload
                    opt Encrypt response
                        kbs ->> kbs: Encrypt with TEE PubKey
                    end
                    kbs -->> cdh: Decryption key payload
                end
            end

            cdh ->> cdh: Decrypt image layer
        end
    end

    cdh -->> kata_agent: Image ready
    kata_agent ->> kata_agent: Create Pod
    kata_agent -->> kata_runtime: Pod created
    kata_runtime -->> k8s: Pod created
```

### POST /launch-policy
#### Requires Admin?
- Yes
#### Request Params:
- A JSON Object containing:
 ```json
 {
    "policy": "< base64-encoded rego policy >",
    "incr_gsvn": bool   //optional, default false
}
 ```

#### Request Response Body:
- OK,`{"gsvn": <MAGS value after operation: int>}`


#### Expected usage:

```shell
encoded_policy=$(base64 <<EOF
package policy
import rego.v1
default authorized := true
EOF)
payload="$(jq --args policy "$encoded_policy" '{"policy": $policy}')"

kbs_host=localhost
kbs_api_port=8080
curl -X POST \
    -H "Content-Type: application/json" \
    -d "$payload" \
    http://$kbs_host:$kbs_api_port/kbs/v0/sams/launch-policy 

# Expected response: '{"gsvn": 0}'
```
